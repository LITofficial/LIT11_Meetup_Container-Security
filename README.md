- **부제:** Trivy기반 클라우드 환경의 컨테이너 이미지 취약점 분석 및 검증
- **발표자:** 지기석, 한영현

## 서론

### 0-1. 용어부터 간단히

| 용어 | 설명 |
| --- | --- |
| **이미지** | 앱 실행에 필요한 것(프로그램, 패키지, 설정)을 한 번에 담아둔 설치 꾸러미 |
| **패키지** | 남이 만들어 둔 부품 |
| **컨테이너** | 그 이미지를 실제로 실행한 것 |
| **배포** | 만든 서비스를 인터넷에 올려서 사람들이 쓸 수 있게 하는 것 |

> 4개 최대한 쉽게 설명

### 0-2. 시나리오: 한 개발자의 배포

*(시나리오나 그림 기반으로)*

1. 개발자가 인터넷으로 받은 프로그램, 패키지, 설정들을 기반으로 서비스를 만들어 배포 (문제 X)
2. 몇 달 뒤, 업로드한 이미지 속 패키지 중 하나에서 보안 취약점 발견, 개발자는 모르는 상태
    - 실제 사례: **Log4j**라는 로그 기록 패키지에서 발견된 구멍
3. 공격자가 해당 취약점을 이용해 컨테이너로 침입
4. 컨테이너들이 한 건물 안에서 방을 나눠 쓰는 구조라, 한 방이 뚫리면 옆방과 건물 전체까지 위험해질 수 있음

**⇒ 데이터 유출 및 서버 위협**

> 호스트, 커널이라는 단어는 쓰지 않고 비유로만

### 0-3. 문제 제기

> **그렇다면 개발자가 배포 전, 이러한 취약점이 존재하는지 미리 알 수는 없을까?**

⇒ 답을 찾기 전에, 컨테이너가 어떤 흐름으로 서비스가 되는지 먼저 보자

## 1. 발표 구성

### 1-1. 클라우드에서는 컨테이너를 어떻게 제공하는가

**Azure 기준**

**그림 하나:**

```
만들고(빌드)  →  창고에 올리고(Push)  →  실행(배포)
```

### 1-2. 보안은 어느 단계에서 하는가

*1-1의 흐름을 그대로 가져옴*

| 단계 | 보안 방법 | 비고 |
| --- | --- | --- |
| **빌드** | 이미지 속 패키지 점검 | **이번 발표의 주제** |
| **Push** | 이미지 창고 접근 권한 관리 | |
| **배포** | 실행 권한 최소화 (최소 권한) | |

- 각 단계마다 지키는 방법이 따로 있다고 말로만 소개
- 이번 발표는 **빌드 단계, 이미지 속 패키지 취약점**에 집중

### 1-3. 취약점(CVE)이란

**취약점** = 패키지에서 발견된 보안 구멍

**왜 생기나**

- 패키지도 결국 사람이 만든 프로그램이라 실수가 섞일 수 있음. 만든 사람도 몰랐다가 몇 달, 몇 년 뒤에 누군가 발견하는 경우가 많음

**Log4j의 구멍**

- 로그(기록)에 적을 글자 안에 숨은 명령을, 그냥 글자가 아니라 진짜 명령으로 착각해서 실행해버림

⇒ 공격자가 글자 한 줄만 보내도 서버를 조종할 수 있었음

**CVE** = 이미 알려진 보안 구멍에 붙은 번호(이름표)

- 예를 들어 서론 0-2의 시나리오는 Log4j의 취약점이며 번호는 `CVE-2021-44228`

- 이런 CVE들은 Trivy에 목록(DB)으로 모여 있어서, 이미지 속 패키지와 대조하면 찾아낼 수 있음

### 1-4. 취약점 분석 도구: Trivy

그 목록과 이미지를 대조해서 배포 전에 찾아주는 도구가 **Trivy**

#### Trivy의 장점

1. **설치가 쉬움**
    - 명령어 한 줄이면 바로 검사할 수 있음
2. **결과를 정리된 표로 줌**
    - 줄글(손글씨 메모)이면 사람이 일일이 읽어야 하지만, 정리된 표(엑셀)로 받으면 우리 프로그램이 "심각한 게 있나?"를 알아서 확인하고 Pass/Fail을 정할 수 있음
    - *(슬라이드 작은 글씨로만 "JSON 출력" 표기, 발표에서는 말하지 않음)*

⇒ 이 두 번째 이유 때문에 **Trivy의 결과를 읽고 판정하는 부분을 우리가 따로 만든 것**

> 그림에서 Trivy가 하는 일(취약점 찾기)과 우리가 만든 부분(Pass/Fail 판정, 레포트)을 **색으로 구분**

#### 구성

```
이미지  →  Trivy 스캔  →  Pass / Fail
```

#### 분석 원리

```
이미지 속 패키지 목록 꺼내기  →  알려진 취약점 DB와 대조  →  위험도 등급
```

#### 위험도 등급

`Critical` / `High` / `Medium` / `Low`

#### 판정 기준

> **Critical이 있으면 Fail, 배포 차단**

### 1-5. 시연 시나리오 소개

**흐름:** 서론의 취약 이미지 스캔 → 차단 → 패치 → 재스캔 통과

결과는 레포트로 출력되게 구현

**시연에서 보여줄 포인트**

1. 취약점이 존재하는 이미지 배포 → 탐지/차단 (레포트)
2. 1의 결과를 통해 문제 분석 및 취약점이 존재하는 이미지 버전 업데이트 → 재배포 → 통과 (레포트)

## 2. 시연

### 2-1. 취약 이미지 준비 및 스캔 실행

서론 시나리오와 같은 이미지 사용 (구버전 Log4j가 든 자바 앱 기반)

### 2-2. 결과 해석

**볼 것 세 가지:** 심각도, 패키지, 올릴 버전 (최대한 쉽게 설명)

⇒ 방치하면 어떤 일이 생기나, 새 버전으로 바꾸면 무엇이 막히나 한두 문장, 간단하고 쉽게

### 2-3. 배포 차단

Fail 로그 확인 및 해당 로그가 의미하는 것이 뭔지 (배포를 막은 것을 확인할 수 있다)

### 2-4. 패치 후 재스캔

패치된 이미지 스캔, Pass 확인

### 2-5. 레포트 확인

시연 중 출력된 결과물 (Pass / Fail 두 개) 확인
